# coding-protocol v2.0.0 plan

Status: approved 2026-11-14. Built as a stack of five PRs, this plan at the bottom.

## What v2 is

Everything breaking, in one release:

1. A slim always-on core, with the workflow rules moved into a router skill.
2. A merge gate: approval no longer merges on its own.
3. A `setup` skill that installs and upgrades all of it.

Additive work from the pstack comparison (proof standard, debugging rewrite,
reusable verification harness, swarm contract) waits for 2.1 and later.

## Decisions made

1. Labels `merge-auto` and `merge-human`, set by the reviewer only.
2. Auto-merge needs approval and `merge-auto`.
3. `ssa-ship` gets `merge-auto` when the path check finds nothing on the ask
   list. The reviewer adds it without reading the diff.
4. `merge-auto` survives a push when the patch is unchanged. Any other push
   removes it. "Unchanged" keeps whitespace: a re-indented line is a change.
5. An agent reviewer's approval is enough to approve. Whether automation may
   merge is the reviewer's separate call.
6. Guardrails stay always-on. Workflow rules move to a router skill that also
   loads on its own description.
7. Enforcement ships as a composite action in this repo, pinned by tag.
8. Tests use `node:test`. Config is JSON. Review round limit defaults to 3.
9. This is 2.0.0.
10. The router skill is named `run`.

## Design

### The always-on core

`AGENTS.md` above the Project divider shrinks to:

- The trust boundary paragraph and the non-interactive fallback, unchanged.
- Before changing code, load the `run` skill.
- Atomic conventional commits. Never commit to `main`. Stage by path.
- Every PR carries exactly one `ssa-*` label. The ask list forces `ssa-ask`.
- A merge needs approval and `merge-auto`. Only the reviewer sets `merge-*`.
- Unattended runs follow `unattended-run`.
- Comment only the why.
- Communicate concisely.
- "Steps" means a runbook.

A rule leaves this list once a check enforces it.

### The router skill (`run`)

Holds the eight workflow rules that left the core: propose before building,
the PR size budget, the test bar, browser-verified UI, docs before memory,
sync docs, check cadence, clean breaks.

It matches the task and names what to load:

| Task | Loads |
|---|---|
| Feature | `coding-process`, `testing`, `stacked-prs`, then `verify-ui` and `sync-docs` as they apply |
| Bug fix | `coding-process` (Debugging), `testing` |
| Refactor | `coding-process`, `testing` |
| Opening a PR | `stacked-prs`, `ship-show-ask`, `sync-docs` |
| Reviewing a PR | `ship-show-ask`, `merge-gate` |
| Unattended run | `unattended-run`, plus the row for the task |

Model invocation stays on, so it loads from its description as well as from
the slash command.

### The merge gate

| State | Meaning |
|---|---|
| No `merge-*` label | Not decided. Nothing auto-merges. |
| `merge-auto` | Automation may merge once approved and green. |
| `merge-human` | A person lands this. Wins if both labels are present. |

What the reviewer does (`merge-gate` skill):

- `ssa-ship`: if `label-check` is green, approve and add `merge-auto`. If it
  is red, say the label is wrong and stop.
- `ssa-show`: review, approve, add `merge-auto` unless a finding is blocking.
- `ssa-ask`: review by running the change. Add `merge-human` when the change
  is irreversible (destructive migration, money movement, auth model, tenant
  scoping), when safety could not be shown by a run, or when review passed the
  round limit. Add `merge-auto` otherwise.
- Approve first, then add the label. The gate ties `merge-auto` to the
  approval it follows.
- After a push that removed `merge-auto`, review the new head, approve it,
  then add the label again.
- A person on the `humans` list lands a `merge-human` PR by removing that
  label and adding `merge-auto`. A required check blocks a manual merge too,
  so this relabel is the human path. A removal by anyone else is ignored.
- Stacks: each stage carries its own label. A stack merge stops below the
  first stage that lacks approval plus `merge-auto`.

### Enforcement

Two required status checks from one workflow.

`label-check` passes when:
- the PR has exactly one `ssa-*` label
- if any changed file matches an ask-list glob, that label is `ssa-ask`

`merge-gate` passes when:
- `label-check` passes
- `merge-human` is not in force
- `merge-auto` is present, last added by an account in `merge_approvers`
- the latest approval from a merge approver covers the current head: the same
  commit, or the same patch
- `merge-auto` was added at or after that approval

Every evaluation checks all five, whatever event triggered it. Nothing depends
on having processed an earlier push.

"The same patch" compares a fingerprint of the PR's whole diff at the approved
commit and at the head. The fingerprint drops only what a rebase changes
(blob ids and hunk line numbers) and keeps every content line byte for byte.
`git patch-id` is not used: it ignores whitespace, so it reads a re-indented
`return` as no change. A diff with binary content, or one that cannot be
fetched, never matches.

When `merge-auto` is present and the approval no longer covers the head, the
workflow removes the label and leaves one comment saying why. That removal is
housekeeping: the check is already red without it.

The workflow uses `pull_request_target`, so it runs the copy on the default
branch and a PR cannot edit its own gate. It fetches git objects to compute
the diff and never checks out or executes PR code.

Config is `.github/coding-protocol.json`, read from the default branch:

```json
{
  "merge_approvers": ["<reviewer-account>", "<maintainer>"],
  "humans": ["<maintainer>"],
  "ask_paths": ["**/migrations/**", "**/auth/**", "**/billing/**"],
  "max_review_rounds": 3
}
```

`.github/**` is always an ask path, so a PR that changes the gate or its
config is itself an Ask.

Tags: `coding-protocol-v2.0.0`, plus a moving `coding-protocol-v2` that
consumer workflows can follow for gate fixes.

## The stack

Every stage is `ssa-ask`. Release metadata lands once, in stage 4.

### Stage 1: slim core and router (about 250 lines)

1. New `skills/run/SKILL.md` with the eight workflow rules and the task
   table.
2. `AGENTS.md`: reduce to the core above, without the merge line yet.
3. README: the packaging table and "What it enforces" reflect the split.
4. `scripts/validate.py`: still resolves every skill the core names.

Done when: validation passes, and every rule from the 1.3.0 core appears in
exactly one place (the new core or `run`). A checklist of the 14 goes in the
PR body.

### Stage 2: merge gate text (about 200 lines)

1. New `skills/merge-gate/SKILL.md`.
2. `AGENTS.md`: the merge line. Project gates gain `Merge approvers`,
   `Review round limit` and a pointer to the config file.
3. `ship-show-ask`: reviewing points at `merge-gate`; approval is not
   permission to merge.
4. `stacked-prs`: the `gh stack merge` walk checks `merge-auto` as well as
   `reviewDecision`.
5. `unattended-run`: checkpoint 4 names `merge-human`.
6. `run`: the review row loads `merge-gate`.

Done when: validation passes, and no skill contradicts another on who may
merge.

### Stage 3: enforcement (about 350 lines)

1. `.github/actions/merge-gate/`: `action.yml` plus `gate.mjs`. The decision
   is a pure function from (labels, changed files, label events, reviews,
   config) to (label-check result, merge-gate result, keep or remove).
2. Unit tests with `node:test`: every condition in the two pass lists, both
   labels present, an author-applied label, a missing config.
3. Integration test: a temporary git repo that rebases a branch cleanly, then
   edits it, and asserts keep then remove from real `git diff` output. A
   regression for a change that is only indentation.
4. CI: run the tests in `validate.yml`.

Done when: tests pass, and each has been seen to fail against a broken
decision function.

### Stage 4: setup, upgrade and release (about 300 lines)

1. New `skills/setup/SKILL.md`: creates the five labels, writes the core and
   Project gates into `AGENTS.md`, writes the config file and caller workflow,
   then reports the branch protection settings it could not set.
2. Upgrade from 1.x: detect the old header, replace the core, keep the
   Project gates, add the new gate lines.
3. Templates for the caller workflow and config file.
4. `ship-show-ask`: label creation moves to `setup`, with a pointer left
   behind.
5. README install section, CHANGELOG with "Upgrading from 1.x", version 2.0.0
   in `plugin.json`, `marketplace.json` and the `AGENTS.md` header.
6. E2E against a scratch repo: fresh install, then a 1.3.0 upgrade. Open a PR
   and confirm auto-merge is blocked without `merge-auto`, blocked when the
   author adds it, and allowed when an approver adds it. Then a `merge-human`
   PR: automation cannot merge it, and a person on `humans` can after
   relabelling.

Done when: both installs and the four merge outcomes are recorded in the
PR's Testing section.

## Verified against current docs

- `pull_request_target` loads the workflow from the repository's default
  branch, and a checkout with no ref also uses the default branch.
- Checks from `pull_request_target` runs count as required status checks.
- A merge queue needs the workflow to also trigger on `merge_group`, or the
  required check never reports.

## Not yet verified (first task of the stage that needs it)

- Stage 3: that an approved commit can still be compared after a force-push
  replaces it. If not, the approval stops covering the head, which is the
  safe failure.
- Stage 3: `path.matchesGlob` on the runner's Node version. If it is not
  stable, a glob package is needed.
- Stage 3: how the gate reports on `merge_group`, where there are no PR
  labels. Proposed: pass, because the gate already held at enqueue.
- Stage 4: whether `gh stack merge` refuses a stage whose required checks are
  red. Upper stages target stage branches, which branch protection on `main`
  does not cover, so this may need a ruleset on all branches.

## Out of scope for 2.0.0

Swarm verification on the reviewer side, the proof standard, the debugging
rewrite, and the reusable verification harness. Each gets its own plan.

## Amendments

Decided during the build, inside the approved design.

- **Review findings on the design.** The human path for `merge-human`, the
  whitespace-preserving patch check and tying `merge-auto` to an approval
  came from review of the stack. They are written into the Design section
  above, which is the current design.
- **"The same patch" (stage 3).** The Design section describes a fingerprint
  of the diff. Review showed any diff comparison that survives a rebase has
  to discard positions, and then the same edit moved to another function
  matches. The gate instead replays the approved commit onto the head's base
  with `git merge-tree` and compares whole trees. It fetches the commits it
  needs as objects; it still checks nothing out.
- **Auto-merge (stage 2).** The author arms auto-merge only after checking
  that the base branch requires `merge-gate`. Without that, auto-merge lands
  on approval alone.
- **Building from a spec (added to scope 2026-11-14).** Approved after the
  stack was reviewed, as a seventh PR: a spec a maintainer hands over counts
  as the approved plan for what it decides, so the agent proposes only the
  gaps.
- **`uninstall`, and inferred Project gates (added to scope 2026-11-14).** An
  eighth PR: a skill that reverses `setup`, and `setup` reading the repo to
  fill in the Project gates before asking for confirmation.
- **`delegate` (added to scope 2026-11-14).** A ninth PR: delegation becomes
  its own skill and a default, loaded from `coding-process`, `unattended-run`
  and `run`.
- **`usage-limits` (added to scope 2026-11-14).** A tenth PR, adapted from
  Builder.io's `stay-within-limits`.
- **`gh stack` (all stages).** Approved, but not usable in the build
  environment: the extension could not be installed there. The stack was
  built with plain git and the GitHub REST API, each PR targeting the branch
  below it. It can't be landed with `gh stack merge`; land it bottom-up.
